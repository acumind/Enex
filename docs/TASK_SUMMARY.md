## Observations & Decisions Made During Sprint 3

### 1. SHA-256 for OTP hashing (not bcrypt)

OTPs are short-lived (5 min) and rate-limited (5 attempts). SHA-256 is sufficient and avoids the ~250ms bcrypt overhead on each verification. Constant-time comparison via `hmac.compare_digest` prevents timing attacks.

### 2. Refresh token allowlist in Redis (fail-closed)

Unlike rate limiting (fail-open), the refresh token allowlist is **fail-closed** — if Redis is unavailable, refresh requests are denied. This prevents unauthorized token reuse if the revocation list is unavailable.

### 3. Access token in memory, refresh token in httpOnly cookie

Access tokens are held in React state (memory) and never stored in localStorage. Refresh tokens are set as `httpOnly`, `secure`, `samesite=strict` cookies scoped to `/api/v1/auth`. This prevents XSS from stealing either token type.

### 4. Account linking by email (auto-merge)

When a user logs in via Google OAuth and their email matches an existing OTP user, the accounts are automatically linked. The `auth_methods` array tracks all methods the user has used (e.g., `["email", "google"]`).

### 5. Timezone-naive datetimes in PostgreSQL

The OTP `expires_at` and `created_at` columns use `TIMESTAMP WITHOUT TIME ZONE`. All Python datetime values must have `tzinfo=None` before being sent to asyncpg. The pattern `datetime.now(UTC).replace(tzinfo=None)` is used consistently.

### 6. NextAuth v5 used only for Google OAuth redirect

NextAuth handles only the Google OAuth redirect flow. All JWT issuance and session management is done by the backend. The NextAuth session callback exposes the Google `id_token` to the client, which then exchanges it with the backend's `/auth/google` endpoint.

### 7. Next.js 16 middleware deprecation warning

Next.js 16 shows a deprecation warning for `middleware.ts` in favor of the new `proxy` convention. The middleware still works correctly. Migration to `proxy` can be done in a future sprint.

## Observations & Decisions Made During Sprint 2

### 1. Lazy imports for Celery tasks and heavy dependencies

All Celery task files (`jobs/extraction.py`, `jobs/archive.py`) and the rate limiter use **lazy imports** (inside functions) for database sessions, repositories, and services. This prevents circular imports and avoids initializing DB connections at module import time — critical for Celery workers which have a different lifecycle than FastAPI.

**Testing implication:** `unittest.mock.patch()` must target the **source module** (e.g., `app.services.extraction.ExtractionService`), not the importing module (e.g., `app.jobs.extraction.ExtractionService`), because lazy imports don't create module-level attributes on the importer.

### 2. Redis rate limiting uses fail-open pattern

The rate limiter catches all non-HTTP exceptions and allows the request through. This means if Redis goes down, the app continues to work (without rate limiting) rather than returning 500 errors. The `redis.asyncio` import is also lazy (inside the `check()` method).

### 3. Prediction duplicate detection uses ±5% price, ±30 days

The `find_duplicate` method matches predictions with the same predictor + stock + target price within 5% + date within 30 days, among `pending_review` or `approved` status predictions. This prevents accidental re-submissions while allowing legitimately different predictions.

### 4. Background task architecture: sync Celery → async services

Celery tasks are synchronous functions that use `asyncio.run()` to bridge into the async service/repository layer. Each task creates its own `async_session_factory()` context rather than using FastAPI's request-scoped sessions.

### 5. Suggestion promote flow is asynchronous

When a moderator promotes a suggestion, the API immediately returns success (status=promoted) and dispatches a Celery task for the actual extraction. The `promoted_to` field on the suggestion is updated by the background task after extraction completes.

### 6. Frontend uses client-side rendering for all interactive pages

All Sprint 2 pages (submit, suggest, dashboard, admin) are client components using TanStack Query for data fetching and state management. Server-side rendering is deferred to Sprint 4 when public pages (leaderboard, profiles) need SSR/SSG for SEO.

## Observations & Decisions Made During Sprint 1

### 1. Cursor-based pagination throughout

All list endpoints use cursor-based pagination (using `created_at` timestamps) instead of offset-based pagination. This provides consistent performance regardless of dataset size and avoids the "shifting window" problem when new items are inserted.

### 2. `require_role()` supports role hierarchy

The auth middleware checks `user.role in allowed_roles`. Admin endpoints pass `("admin",)`, moderator endpoints pass `("moderator", "admin")`, allowing admins to access moderator-only endpoints automatically.

### 3. Stock seeding uses ON CONFLICT DO NOTHING

`StockService.seed_from_csv()` uses bulk insert with `ON CONFLICT (symbol) DO NOTHING`, making the seed operation idempotent — safe to run multiple times without duplicating data.

### 4. Prediction service validates foreign keys before creation

The service layer checks that `predictor_id` and `stock_id` exist before creating a prediction, raising `NotFoundError` with descriptive messages rather than letting the database FK constraint produce a cryptic error.

## Observations & Decisions Made During Sprint 0

### 1. Node.js version bump: 18 -> 20

The plan specified Node 18 for the CI and Dockerfile, but **Next.js 16.x (latest as of create-next-app) requires Node >= 20.9.0**. Both the Dockerfile and CI workflow were updated to use Node 20. Future sprints should use Node 20+ everywhere.

### 2. Next.js version is 16.x, not 15

Running `create-next-app@latest` installed **Next.js 16.1.6** (with React 19.2.3). This is the current latest stable. The plan was written when Next.js 15 was current. This is fully backwards-compatible — App Router, RSC, standalone output all work the same way.

### 3. Tailwind CSS v4 (not v3)

Shadcn/ui now initializes with **Tailwind CSS v4**, which uses CSS-first configuration instead of `tailwind.config.ts`. The `globals.css` file contains all theme configuration via `@theme` directives. No `tailwind.config.ts` file exists — this is intentional with v4.

### 4. Alembic auto-generated migration excluded from linting

The auto-generated migration file uses old-style `Union[str, None]` types, long lines, and unsorted imports. Rather than manually reformatting (which would break on future auto-generates), `migrations/versions/` is excluded from ruff via `extend-exclude`. This is the standard practice.

### 5. FastAPI `Depends()` B008 suppression

Ruff rule B008 flags `Depends()` calls in default arguments. This is an intentional FastAPI pattern, so `app/api/**` files have `B008` suppressed via `per-file-ignores`.

### 6. MyPy strict mode — third-party overrides needed

Several libraries lack complete type stubs: `celery`, `jose`, `passlib`, `yfinance`, `redis`. These are configured with `ignore_missing_imports = true` in `[[tool.mypy.overrides]]`. As the project grows, consider adding `types-redis` and other stub packages.

### 7. SQLAlchemy JSONB columns — generic type annotations

JSONB columns (`social_links`, `auth_methods`, `sector_accuracy`, `data`) use typed generics like `Mapped[dict[str, str]]` and `Mapped[list[str]]` to satisfy mypy strict mode. The actual JSON stored can be more flexible, but the type hints provide baseline safety.

### 8. Python 3.13 used locally (3.12 targeted)

`uv` resolved to Python 3.13.3 locally, while `pyproject.toml` targets `>=3.12` and CI uses 3.12. This is fine — 3.13 is a superset. The Dockerfile pins `python:3.12-slim` for production consistency.

### 9. `upside_pct` generated column not in ORM

The SQL schema defines `upside_pct` as a `GENERATED ALWAYS AS` stored column on the `predictions` table. SQLAlchemy's Alembic autogenerate does not emit this — it would need a manual `op.execute(ALTER TABLE ...)` in a future migration if this computed column is desired at the DB level. For now, this can be computed in the application layer.

### 10. Azure deployment deferred

Dockerfiles are ready but actual Azure Container Apps provisioning requires Azure subscription setup, ACR creation, Key Vault configuration, and managed identity. This is an operational step outside Sprint 0 scope.

## Upcoming Sprints — What to Know Before Starting

### Sprint 3: Authentication & User Login

**Scope:** Three auth paths (Google OAuth, Email OTP, Phone OTP), frontend auth middleware, login/profile pages.

**Prerequisites from Sprint 2:**
- JWT auth with `get_current_user` + `require_role()` already implemented
- Redis rate limiting infrastructure already built (reuse for OTP rate limiting)
- User model has `auth_methods`, `oauth_provider`, `oauth_id` fields ready
- `otp_codes` table already in the migration

**Key implementation points:**
- Backend auth routes: `POST /auth/otp/request`, `POST /auth/otp/verify`, `POST /auth/google`, `POST /auth/refresh`
- Email OTP: generate 6-digit code, hash with `passlib` bcrypt, store in `otp_codes`, send via Resend API
- Phone OTP: same flow but send via MSG91 Verify API
- Google OAuth: frontend NextAuth.js v5 handles OAuth flow → backend verifies Google JWT → issues backend JWT
- Token refresh: issue new refresh token on each use, invalidate the old one
- Frontend: NextAuth.js provider, auth middleware protecting `(user)` and `(admin)` route groups, login page, profile page

**Watch out for:**
- Account linking: if a user logs in with Google and later with phone OTP, match by email to merge accounts
- The `otp_codes` table stores hashed codes — use `passlib` bcrypt for hashing
- MSG91 requires DLT registration for Indian SMS — this is a regulatory setup step, not a code task
- Rate limit OTP requests: 5/hour per identifier (already have the Redis infrastructure from Sprint 2)
- `user_has_identity` CHECK constraint requires at least email or phone — enforce at the API layer too

### Sprint 4: Evaluation Engine

**Scope:** Daily job that compares predictions to actual prices and computes outcomes + scorecard materialization.

**Key implementation points:**
- Price data adapter: `yfinance` integration to download daily OHLCV data for tracked stocks
- Store in `stock_daily_prices` table (stock_id + trade_date unique)
- Evaluation job: daily Celery beat task, finds approved predictions past `default_eval_date`, computes hit/miss/partial_hit
- Tolerance band: exact hit if actual price >= target, partial_hit if within 5%, miss otherwise
- Scorecard computation job: aggregate stats per predictor → `predictor_scorecards` table
- Price fetcher job using `yfinance` to keep `stocks.current_price` up to date

**Watch out for:**
- Stock splits/bonuses affect price comparison — use `adjusted_close` from `stock_daily_prices`
- `yfinance` uses `.NS` suffix for NSE stocks (e.g., `RELIANCE.NS`) — handle this in the price data adapter
- Weekend/holiday handling: if `eval_date` falls on a non-trading day, use the nearest prior trading day
- Celery beat setup: configure periodic task schedule in `celery_app.py`

### Sprint 5: Public Interface & SEO

**Scope:** SSG/ISR pages for leaderboard, predictor profiles, stock pages, search + responsive design.

**Key frontend patterns:**
- Leaderboard: Server Component with ISR (revalidate every 5–10 minutes)
- Predictor profiles: dynamic route `[slug]` with `generateStaticParams` for popular predictors
- Use TanStack Query for client-side data fetching on interactive pages
- Zustand for client state (filters, sort preferences, theme)
- Recharts or Tremor for accuracy trend charts

**Watch out for:**
- SEO is critical for this sprint — every predictor profile needs proper `<title>`, `description`, and OpenGraph tags
- The `predictor_scorecards` table must have `total_predictions >= 10` for the accuracy index — handle "insufficient data" display
- Cursor-based pagination already implemented on all list endpoints — frontend just needs to wire it up

## Architecture Patterns Reference

### Backend Layer Responsibilities

```
Route (app/api/routes/)      → HTTP concerns: parse request, validate input, return response
Service (app/services/)      → Business logic: orchestrate operations, enforce rules
Repository (app/repositories/) → Data access: SQL queries, ORM operations
Model (app/models/)          → Schema definition: tables, columns, constraints
Schema (app/schemas/)        → API contracts: Pydantic request/response models
Integration (app/integrations/) → External services: AI, email, SMS, price data
Job (app/jobs/)              → Background tasks: Celery workers, scheduled jobs
```

### External Service Integration Pattern

```python
# app/integrations/email/protocol.py
from typing import Protocol

class EmailProvider(Protocol):
    async def send(self, to: str, subject: str, body: str) -> bool: ...

# app/integrations/email/resend_adapter.py
class ResendAdapter:
    async def send(self, to: str, subject: str, body: str) -> bool:
        # Resend API call
        ...

# app/core/deps.py — wire via DI
def get_email_provider() -> EmailProvider:
    if settings.EMAIL_PROVIDER == "resend":
        return ResendAdapter(api_key=settings.RESEND_API_KEY)
    ...
```

### Frontend Route Groups

```
app/
  (public)/    → SSG/ISR pages, no auth required (leaderboard, profiles, stocks)
  (auth)/      → Login/register pages
  (user)/      → Authenticated user pages (dashboard, watchlist, submissions)
  (admin)/     → Admin/moderator pages (review queue, user management)
```
